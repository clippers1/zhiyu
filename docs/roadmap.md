# 知愈项目拓展计划

基线版本：`0.0.1-beta.1`。本文件是后续工作的建议方案，不表示相关功能已经实现，也不构成上线时间承诺。按阶段推进，实际版本范围根据用户反馈与维护能力调整。

`0.0.1-beta.2` 进展：History、最小内容平台、现有内容迁移、正式/演示 API、审校权限、发布回滚撤回及备份工具已落地。血糖等既有内容仍待真实专业审校。使用方式与当前限制见 [平台说明](content-platform.md)；以下产品体验与真实用户研究目标不因技术实现而视为完成。

`0.0.1-beta.3` 进展：已补读者纠错、版本绑定提交、后台处理、凭码查询/删除，以及来源复核排期和维护待办，见 [纠错与来源复核](feedback-and-maintenance.md)。下一项可独立推进的工程工作是 C2 公开文章预渲染；C3 真实审校仍依赖专业人员，不以功能上线代替内容质量验收。

2026-09-19 更新：面向大众 ToC 医学科普，提前建设来源管理、内容后台与审校流程；不再等到内容规模变大才引入后端。History 路由本轮实现，公开文章预渲染列入后续里程碑。详细依据见 [产品规划](product-plan.md)、[知识平台](knowledge-platform.md) 和 [渲染决策](rendering-and-routing.md)。

## 产品方向

先帮助普通读者完成一条清晰的阅读路径：找到一个体检术语 → 理解它与身体的关系 → 查到知识来源 → 保存或分享给需要的人。在这一体验得到验证后，再扩大内容规模与访问渠道。

基线版本具备 React + Vite 移动端前端、8 个专题、静态内容访问层、Hash 路由、本地收藏、来源引用及自动化测试；已完成 HTTPS 部署。后续 Beta 已实现 History、内容后台及维护闭环。当前仍缺少真实用户研究、专业审校记录、公开文章预渲染和跨端客户端。

先验证三个假设：读者能找到想了解的术语；图文与器官关联能帮助理解；收藏或分享对后续使用有价值。暂不假设用户需要注册、上传报告或安装 App。

以下章节保留规划时的工作领域与候选版本，实际完成范围以上方版本进展及 CHANGELOG 为准，不能把整个阶段视为已经验收。

## 1. 下一版 Beta：完成可靠的阅读闭环

候选版本为 `0.0.1-beta.2`，优先做以下工作：

1. **观察真实阅读过程。** 招募至少 5 位目标读者，使用预设科普问题测试查找专题、理解关联、找到来源和再次打开收藏。记录完成情况、耗时、困惑与错误理解，不收集个人体检报告。
2. **把内容结构固定下来。** 建立内容字段约束，验证唯一 ID、分类、引用编号、关联专题和审核字段；考虑从正文生成摘要索引，减少两处手工维护产生的不一致。
3. **完成现有内容审校。** 为正式展示内容记录审校人、审校时间、内容版本及依据；保留修改记录。当前测试将状态固定为 `pending`，届时应改为验证不同状态对应的必填信息。
4. **补真实设备与可访问性检查。** 覆盖 iOS Safari、Android Chrome 与微信内置浏览器，检查键盘操作、弹窗焦点、字体放大、安全区和弱网失败重试。
5. **建立基础交付流程。** 在持续集成中执行内容测试、生产构建和核心交互测试，记录版本变更。由维护者确定许可证后，再补充相应授权与贡献文件。

建议验收目标：至少 4/5 位试用者无需提示完成查找、查看来源与收藏回访；核心任务无阻断问题；拟作为已审校内容展示的专题具有完整审校记录。该比例仅作为小样本可用性检查门槛，不视为总体用户表现。理解效果通过复述观察，先形成基线，再设量化目标。

依赖：目标读者参与、具备相关专业背景的审校协作者、真实设备。若审校资源未到位，版本继续保持待审校 Beta 定位。

## 2. 内容扩展：优先补用户实际查找的知识

候选选题包括血常规、肝功能、肾功能、尿常规及甲状腺相关指标。按反馈频率、来源可靠性、解释难度和审校能力选择首批内容，具体数量以能持续维护为准。

- 为每个专题统一定义：是什么、与哪些器官相关、术语含义、常见误解、理解时需要的背景、参考资料。
- 补充中文别名与常见缩写，帮助用户从体检单上的名称找到专题。
- 检查器官页出现的指标是否有可阅读的关联专题，避免出现没有内容承接的入口。
- 对涉及数值阈值的内容，明确指南版本、地域、单位、适用条件与人群，不从单一数值推导个人诊断。

跟踪指标：预设术语查询的命中率、无结果查询所反映的内容缺口、来源失效数量、到期未复核内容数量。先用人工整理的查询集和自愿反馈建立基线；若未来接入分析工具，应先明确采集范围、保留时间和隐私说明。

验收：本批选题均满足内容结构与审校要求，约定的术语查询集能找到对应内容，关联链接无缺失。内容增长后测量索引体积与移动端查找耗时，再决定是否需要更早引入后端。

## 3. 内容服务：支持多人维护和可控发布

医学内容的审核与发布治理已经足以构成建设内容服务的理由，应与首批选题及阅读体验设计并行推进。优先验证 PostgreSQL + Payload CMS，复用现有 `list` / `get` 接口契约；具体 CMS 在编辑流程与授权评估后选择。服务端检索和分页可随公开 API 一起建设，但不为尚未出现的规模问题提前引入复杂搜索集群。

- 分离编辑、审校与发布权限；建立草稿、审校、发布、复核状态及操作记录。
- 支持内容版本、预览、回滚、备份与恢复，公开接口只返回允许公开的内容。
- 服务端处理搜索、分类和分页，保留前端静态适配器用于本地开发与演示。
- 明确缓存刷新机制，避免摘要与正文版本不一致；监测请求失败和内容获取耗时。

验收：编辑者能完成新增、审校、发布、回滚的完整演练；未发布内容无法通过公开接口访问；静态与远程模式通过同一组契约检查；用预期规模的数据测得移动端加载基线；完成一次备份恢复演练。

读者账号和云端收藏不作为 CMS 的前置条件。只有确认跨设备回访需求后，再设计账号、同步、数据导出与删除能力。

## 4. 渠道扩展：根据实际入口选择客户端

先验证公众号菜单或文章链接进入 H5 的路径，使用真实手机检查分享与回访。自定义微信分享卡片需要 JS-SDK 与服务端签名，按实际需要接入。

| 选项 | 优先选择的信号 | 可复用部分 | 新增工作 |
| --- | --- | --- | --- |
| 小程序 | 用户主要在微信中查找与回访，H5 入口存在明确障碍 | 内容模型、接口、术语与信息结构 | 页面路由、组件、存储、交互图形、来源展示及平台审核；可评估 Taro |
| App | 出现持续使用、离线阅读或原生系统能力的明确需求 | H5 页面和内容服务，视技术方案而定 | 可先评估 Capacitor；补离线更新、原生分享、签名、分发及真实设备验证 |

同时开发多个客户端会增加内容展示与测试成本，首轮只选择一个新增渠道。验收以新入口的核心阅读任务完成情况、回访情况和维护成本为依据，先采集基线，不预设增长百分比。

本轮已将前端切换为 History 并兼容旧 Hash 链接。公开文章和专题建议采用 SSG / ISR，收藏、搜索与器官交互保留客户端能力；不要求全站动态 SSR。小程序路由仍需要独立适配。

## 暂缓事项与待确认决策

暂缓个人报告上传、OCR、个人健康档案、AI 个体化解读与付费服务。这些能力需要单独验证用户需求，并设计数据处理、医学质量和运营流程，不纳入当前 Beta 扩展范围。

需要逐步确认：目标读者的首要使用场景、可投入的审校资源、首批扩展选题、开源许可证，以及后续主要入口是网站、微信还是 App。当前计划先以“拿到体检结果后查术语的普通读者”为工作假设，不等待所有决策完成才开展阅读验证与内容结构整理。
