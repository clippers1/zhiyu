# 读者纠错与来源复核（0.0.1-beta.3）

本阶段补齐“读者发现问题 → 编辑收到并处理 → 读者查询回复”的维护流程，不新增或自动批准医学观点。既有 8 篇演示内容仍为待专业审校，既有来源不被自动标记为已检查或已授权。

## 读者如何反馈

指标与器官页的知识来源下方提供“向编辑反馈”。选择内容准确性、来源问题、表达理解或页面体验，填写 10–1500 字的说明，确认没有填写个人信息后提交。服务端绑定当前发布集合、文章和修订，标题从数据库读取，不信任浏览器提交的标题。

提交后保留 64 位专属查询码，从所有页面底部的“查询纠错进度”查看状态与编辑说明，也可以主动删除这条反馈。查询码不会自动放入本地存储，也不出现在链接中；数据库只保存 SHA-256 哈希。任何持码者都可查询和删除，应把它当作私密凭证保管。遗失后不提供身份找回。

提交结果不确定时可使用已有查询码查询，或重试同一内容；浏览器为相同的一次填写复用查询码，后台唯一约束避免重复建单。修改填写内容会生成新的查询码。页面版本已经更新时，首次提交返回冲突，要求读者刷新后重新核对；内容已撤回时拒绝新反馈，但已有查询码仍可查询或删除。

这不是问诊渠道，不接受报告附件，不要求手机号、邮箱、姓名或病史，也不提供紧急帮助或即时处理承诺。自由文本仍可能被误填个人信息，维护者应及时删除不必要的敏感内容，不能把“表单不要求”理解为“永远不会收到”。

## 编辑如何处理

后台“读者纠错队列”仅管理员和内容编辑可读、可更新；医学审校或发布角色不因角色名称而默认获得读者原始反馈。管理员可分配负责人；编辑可处理队列并选取自己可见的成员。管理员和持有查询码的读者可以删除记录。

处理状态：已收到 → 处理中 / 等待专业复核 → 已处理 / 暂不调整。状态允许重新打开；结束处理必须写清给读者的说明，不要求编辑在尚未完成专业复核时强行结案。原始问题、对应修订和集合不可编辑。内部备注与读者回复分开，查询接口只返回标题、版本、状态、回复和时间，不返回原始问题、内部备注、负责人、查询码哈希或内部 ID。

修改状态或回复、删除反馈会追加审计；审计只记录目标和动作，不复制问题正文或查询码。**将反馈设为“已处理”不会修改正文，也不会自动产生医学审校或发布记录。** 如果确需改文，仍须编辑草稿、专业审校、创建修订和显式发布；必要时先撤回不安全内容。

反馈保留至读者主动删除或维护者清理，当前没有自动保留期清理任务。删除移除在线反馈正文与回复、使查询码失效，但不回写已经生成的数据库备份；备份副本随维护者的保留周期清理。禁止把反馈或生产数据库导出到公开仓库。该说明描述当前实现，不宣称已完成特定地区的法律合规评估。

## 来源复核待办

来源记录新增：下次人工复核日期、最近检查结果、内部复核说明。既有记录的下次日期保持空白，检查结果默认为“尚未重新检查”，不伪造一次实际检查。

后台首页展示：到期来源数量、未安排复核数量、来源变化/不可用数量、待处理反馈数量；点击进入对应筛选。最多列出 5 条到期或有问题的来源，并链接到当前引用它的草稿。历史发布快照不会随来源修改而变化，编辑还需检查相关发布入口。

操作顺序：打开原文 → 人工检查链接、版本与关键内容 → 填写实际检查结果和核验日期 → 记录说明 → 按内容风险安排下次复核。下次日期须晚于本次核验日期；原文变化或链接不可用时必须记录说明。系统不访问上游网址，因此本轮不引入来源抓取或内网请求风险。

正式审校要求来源当前已确认为可用。来源可用性进入审校指纹；安排下一次日期本身不进入医学审校指纹。到期只是待办提醒，不自动宣称内容错误、不自动撤稿、不自动延长复核周期。来源发生变化时，应评估既有正式和演示集合分别是否需要撤回。

## API 与部署

先备份数据库，再执行包含本版增量迁移的 `npm run payload -- migrate`，之后启动新版 CMS。无需重新导入旧 JSON 或改动发布快照。

前端构建时设置：

```env
VITE_CONTENT_API_BASE_URL=/api/demo
VITE_FEEDBACK_API_BASE_URL=/api/feedback
```

正式内容使用 `/api/v1`。纠错当前采用同源部署；Nginx 继续代理 `/api/`。静态离线演示不设置纠错地址，也不展示无法提交的入口。仅提供已发布修订 `releaseID` 的内容才展示提交表单。

| 端点 | 用途 | 请求正文关键字段 |
| --- | --- | --- |
| `POST /api/feedback/submit` | 提交版本绑定问题 | receipt、kind、slug、channel、releaseID、category、message、consent |
| `POST /api/feedback/status` | 凭码查看状态 | receipt |
| `POST /api/feedback/delete` | 凭码删除反馈 | receipt |

所有请求必须来自 `SERVER_URL` 的 Origin、使用 JSON，查询码只能在正文传递；响应 `no-store`。同源校验是浏览器跨站防护，不是机器人身份认证。请求体最多 8 KiB，提交每个限流身份每小时 5 次，查询与删除各每分钟 30 次，超限返回 429 和 Retry-After。

计数保存在 PostgreSQL，通过原子 UPSERT 跨并发请求和进程生效。密钥 HMAC 派生的窗口标识代替原始 IP；后续请求会清理到期计数，没有流量时不会主动触发清理。Nginx 等基础设施仍可能记录访问 IP，部署者应另行设置日志访问权限与保留策略，不声称整条链路不记录 IP。

`FEEDBACK_TRUST_PROXY` 默认 false：所有请求共用保守限额，忽略客户端提供的地址头。只有 CMS 不能被外网绕过、可信反向代理明确覆盖 `X-Real-IP` 时才能设为 true；示例 Nginx 已覆盖该头且 Compose 只监听回环地址。本实现不信任 `X-Forwarded-For`。多人共享公网 IP 可能共享限额；未实现验证码、分布式攻击防护或全站配额，应根据实际滥用情况进一步配置网关。

## 验证

- 前端单元：`npm run test:feedback`，覆盖查询码、正文传递、不携带 Cookie 和错误提示。
- 隔离后端：`DATABASE_URI` 必须指向 `zhiyu_test`，应用迁移后执行 `npm run test:workflow` 和 `npm run test:feedback`。包含匿名权限、版本冲突、正式/演示隔离、幂等、原始记录不可变、内部备注隔离、删除、来源状态和并发限流。
- 浏览器：对启用两个前端变量的开发站运行 `node scripts/feedback-smoke.mjs`；默认模拟接口，覆盖失败重试、查询码、查询/删除与移动布局。
- 真实链路：显式设置 `FEEDBACK_LIVE=true` 和 `PLAYWRIGHT_BASE_URL`，可额外提供私有 `ADMIN_CREDENTIALS_FILE` 验证后台回复。会提交一条明确标记的合成问题，并通过自己的查询码删除；不得在共享环境中跳过清理。另运行既有 `scripts/smoke.mjs` 覆盖原有阅读流程。
