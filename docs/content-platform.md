# 内容平台使用与维护

> `0.0.1-beta.13` 起，正式集合支持“版本绑定的专业审校”和“基础知识来源整理”两条独立路径，见 [产品规划](product-plan.md) 和 [路线图](roadmap.md)。轻量路径只适用于明确标记的基础解剖、生理和术语；不会把编辑核对显示成医生审校。

本版本实现 PostgreSQL + Payload CMS 的最小内容平台。Next.js 同时承载后台和公开页面，读者界面复用现有 React 组件；Vite 保留为离线演示。公开页面采用无缓存动态 SSR，不是 SSG/ISR，见 [公开页面渲染](public-rendering.md)。

## 已实现的边界

- 来源库、分类、结构化知识编辑、浏览器可操作的后台。
- 角色权限、人工核验医学审校资格、禁止最后编辑者自审。
- 审校绑定正文、适用范围、摘要和来源快照的指纹。
- 基础知识可由发布管理者记录来源、表达与图示边界核对，记录绑定同一不可变快照；旧内容默认按高风险处理。
- 不可修改的内容修订、显式发布入口、版本切换、回滚、撤回及审计记录。
- 正式 API 与演示 API 分开；保存草稿不直接改变网站。
- 导入现有 8 个专题、去重来源，保留稳定 ID 和本地收藏。
- 来源、适用范围和真实审校信息的前端展示；器官与指标关系由数据驱动。
- 数据库迁移、备份脚本和隔离的流程测试。
- 读者纠错队列、查询码回复/删除、来源复核排期与后台首页维护待办，详见 [纠错与来源复核](feedback-and-maintenance.md)。

没有实现自动医学审核、自动抓取医学正文、AI 问答、读者账号、读者健康记录或邮件/站外提醒。来源到期仅在后台待办中提示，实际复核仍需人工完成。医学审校资格与内容质量需要真实专业人员负责。默认没有邮件服务，不支持邮件找回密码；已有管理员可管理成员账户。

## 两个发布集合

| 集合 | API 前缀 | 允许的内容 | 使用场景 |
| --- | --- | --- | --- |
| 正式 | `/api/v1` | 与通过审校匹配，或完成来源整理的低风险基础知识不可变修订 | 正式内容服务，公开区分两种状态 |
| 演示 | `/api/demo` | 管理员显式创建的演示快照，始终返回 `pending` 和 `demo: true` | 明确标识为来源与表达待完整核对的 Beta 演示 |

演示 API 需要 `ENABLE_DEMO_API=true` 明确开启。当前迁移只创建演示修订，没有生成医学审校记录，也没有把旧文件伪装成已审核内容。正式集合在真实审校完成前可以为空。

完整网站使用 `SITE_CONTENT_CHANNEL=demo` 或 `official` 选择集合；独立 Vite 入口仍通过 `VITE_CONTENT_API_BASE_URL` 选择接口，为空时使用静态演示。切换正式集合前，目标内容必须逐篇完成专业审校或符合基础知识来源整理条件，避免网站显示空目录。

所有公开 API 和动态 HTML 使用 `Cache-Control: no-store`，不依赖后台变更后等待 CDN 过期。用户已经打开的旧页面不会被远程抹除，再次请求时获取当前发布内容；以后引入 SSG/ISR 或页面缓存，需要配套撤回与缓存失效机制。

## 后台编辑流程

后台入口为站点的 `/admin`。管理员、编辑、审校人和发布管理员各有独立职责，不需要为读者创建账号。

### 1. 登记参考来源

在“参考来源库”填写原文标题、发布机构、HTTPS 链接、语言、版本/日期、核验日期以及引用/使用权限。

`尚未核对` 是导入默认值。确认使用方式时必须记录依据，不能因为来自官方机构就默认允许全文复制。“仅作为依据链接”适用于原创科普整理的引用方式，不是转载许可。后台不自动访问或复制上游正文。

### 2. 编辑知识草稿

在“知识编辑”填写指标或器官内容。每篇可配置摘要、搜索别名、分类、适用范围、基础解释、指标分工、过程示意、阅读提示、引用和关联内容。

每条引用有本文内唯一编号，例如 `tests`。正文的来源编号填写这些值，多个用逗号分隔。正式发布前应补齐页码、段落标题或原文锚点，以及过程示意等知识点的依据。

稳定标识和内容类型创建后不可修改，以保护链接和收藏。内容有历史版本，可在后台查看。编辑后保存仍只是草稿，不会更改任何已经发布的快照。

人体示意图本身仍绘制了当前五个器官。新增器官文本与列表可从后台维护；如果增加新的解剖交互区域，仍需前端图形设计与实现。

### 3. 医学审校

管理员根据真实资质设置独立成员的“医学审校”角色，并记录资格核验依据。初始管理员没有医学审校资格，系统不会自动创建医生或审校人。

审校人查看目标草稿后，在“医学审校”创建通过或需修订记录。系统捕获当时的正文与来源快照；记录不可修改。最后编辑者不能审校自己的版本。

审批通过前，系统检查适用范围已确认、引用定位已补齐、来源使用权限已记录、来源已人工确认可用、关键段落有来源编号。这些是结构与流程检查，并不证明医学观点正确。

### 3.1 基础知识来源整理

只有内容风险明确为“基础知识（解剖、生理、术语）”时，发布管理者才能选择“基础知识来源整理”。系统仍要求适用范围、具体来源定位、人工可用性、引用/使用方式和所有关键知识点来源完整。

发布时必须记录本次核对的来源、中文表达、图示简化和未覆盖范围。该记录与正文及来源指纹一起保存在不可变修订中；正文或来源变化后必须创建新的来源整理修订。疾病、数值标准、特殊人群及诊疗相关内容不能通过修改提示文案绕过高风险边界。

### 4. 生成修订并上线

发布管理者在“可发布修订”选择草稿、正式集合和发布依据：高风险内容使用匹配的专业审校记录；符合条件的基础知识可填写来源整理核对记录。正文或来源已经变化时，旧修订仍可回滚，但不能冒充新草稿的核对状态。

在“上线 / 回滚 / 撤回”创建该内容的发布入口，选择修订并填写说明。保存后 API 才会展示该快照。同一集合中的同一篇知识只有一个入口。

管理员可显式选择“演示”集合生成待核对修订。演示数据无法直接改成正式状态；必须重新生成满足任一正式发布路径的修订。

### 5. 修订、回滚和撤回

- 正文修订：编辑草稿 → 重新专业审校或重新完成基础知识来源整理 → 创建修订 → 将发布入口指向新修订。
- 回滚：在同一发布入口改选同一内容、同一集合的历史修订，并记录原因。
- 撤回：勾选停止公开展示并填写原因，列表与正文接口随即停止返回该内容。
- 审计：系统追加审校、发布、切换和撤回记录；后台成员不能手工伪造或修改审计记录。

撤回正式集合不会自动撤回同主题的独立演示集合。处理重大问题时应检查所有集合，并分别撤回受影响内容。正式运营时应关闭演示 API。

## 数据结构与版本策略

`sources` 与 `articles` 使用 Payload 历史版本；`reviews` 保存审校指纹及快照；`releases` 保存可展示的不可变正文和摘要；`publications` 表示每个内容当前展示哪个修订。`audit-events` 记录敏感操作。

这里没有另外手写一套与 Payload 重复的通用版本表。公开正文只来自发布快照，不直接读取正在编辑的文章或正在修改的来源。来源变化会阻止旧专业审校用于创建新修订；来源整理路径每次生成新修订时也重新核对当前快照。已经发布的历史快照保持原样，是否需要撤回应由内容负责人判断。

当前搜索使用数据库中的摘要检索字段，支持中文子串、已配置别名、英文缩写、分类和分页；未接入中文分词、拼写纠错或语义搜索。用户输入长度与分页规模有限制，不记录公开用户的搜索历史。

## 本地开发与部署

需要 Docker Compose；直接运行后台时建议 Node.js 22。项目根目录的 `compose.yaml` 启动独立 PostgreSQL 与 CMS。数据库不暴露宿主机端口，CMS 默认仅监听宿主机回环地址。

1. 根据 `deploy/content.env.example` 准备私有环境文件，或运行 `scripts/init-content-env.mjs` 生成随机密钥与初始账号文件。参数为自己选择的绝对私有目录和站点地址；生成器不覆盖已有文件、不打印密钥。
2. 构建与启动数据库：`docker compose --env-file <私有环境文件> up -d db`，然后 `docker compose --env-file <私有环境文件> build cms`。
3. 应用迁移：`docker compose --env-file <私有环境文件> run --rm cms npm run payload -- migrate`。
4. 导入时向一次性 CMS 容器额外提供 `BOOTSTRAP_EMAIL`、`BOOTSTRAP_PASSWORD`、`SEED_CONTENT_DIR` 和可选 `SEED_DEMO=true`；将项目的 `public/content` 只读挂载到 `SEED_CONTENT_DIR`。执行 `npm run seed`。
5. `docker compose --env-file <私有环境文件> up -d cms`，确认 `/api/health` 返回成功。
6. 参考 `deploy/nginx-ssr.conf.example` 将完整网站代理到 Next.js，不再回退 Vite HTML。使用 HTTPS 时，`SERVER_URL` 必须是实际站点来源，`COOKIE_SECURE=true`。
7. 设置 `SITE_CONTENT_CHANNEL` 并重启服务，确认 HTML、API 来自同一集合。首次登录后修改初始密码、设置实际邮箱；随后妥善处理初始密码交付文件。仅需独立 Vite 演示时仍可使用原静态部署方式。

上述 `<私有环境文件>` 是占位说明，执行时替换为实际路径。私有环境、初始密码、数据库数据与备份均不能提交到 Git。生产环境固定 `PAYLOAD_DB_PUSH=false`，采用已提交的数据库迁移，不能用开发模式自动改生产表。

导入脚本可重复执行：不会覆盖已有草稿、创建伪审校、切换已有修订或重新启用已撤回入口。数据库不可用时 API 报错，前端显示失败与重试，不静默切换到可能过期的静态医学内容。

## 验证与备份

- 前端：`npm run test:content`、`npm run test:routes`、`npm run build`。
- 后台：在 `backend` 运行 `npm run typecheck`；容器构建执行生产构建。
- 流程：将 `DATABASE_URI` 指向独立的 `zhiyu_test` 数据库，应用迁移后运行 `npm run test:workflow`。脚本拒绝在其他数据库运行，测试审校身份仅为合成夹具。
- 浏览器：启动站点后执行 `PLAYWRIGHT_BASE_URL=<站点> CONTENT_API_BASE_URL=/api/demo npm run test:ui`。静态模式不要设置 `CONTENT_API_BASE_URL`。
- HTTP：匿名不能访问 CMS 草稿或创建成员；正式接口不能返回待审校演示内容；空收藏返回零条；撤回后列表与详情一致。
- 备份：在项目根目录运行 `node scripts/db-backup.mjs <绝对私有环境路径> <绝对备份文件路径>`。它使用 PostgreSQL 自定义格式导出，并以私有权限保存，失败不会报告成功。
- 恢复：先向独立临时数据库恢复备份，核对来源、知识、修订、发布入口和审计数量，再决定正式恢复。不要直接用恢复命令覆盖运行中的数据库。

默认未创建定时备份或跨机器备份任务；部署维护者仍需根据恢复目标制定周期与保留策略。当前版本提供并验证备份与恢复操作，不把同机备份称为灾难恢复保障。
