# 知愈 ToC 产品规划：从交互原型到大众医学科普产品

日期：2026-09-19。基于 `0.0.1-beta.1` 的代码、内容和现有页面评估。本文是产品方案，除明确注明外，功能均待实现；优先级是基于当前证据的判断，不是已有用户数据得出的结论。

相关文档：[知识来源与内容平台](knowledge-platform.md)、[History 与页面渲染](rendering-and-routing.md)、[实施路线](roadmap.md)。

## 1. 产品判断

知愈适合定位为“普通人遇到健康问题时，能看懂、能核验、知道下一步该了解什么的医学科普工具”。广泛服务大众是长期方向，第一阶段用“体检术语与常见健康疑问”形成完整入口，逐步延伸到疾病基础、检查准备、预防与生活方式。

核心价值是降低理解成本和信息判断成本。器官互动图可以形成视觉辨识度，但用户通常不会只为了看器官图反复回来。真正的吸引力来自具体问题被回答、内容值得相信，以及下一次需要时容易找回。

当前视觉风格和移动阅读基础较完整，明显的原型感更多来自内容与行为：

| 现状及代码依据 | 用户感受 | 产品补足方向 |
| --- | --- | --- |
| 内容索引仅有 3 个指标、5 个器官 | 查两次就看完了，许多问题找不到 | 完成一个领域的覆盖，而非把不同领域各放一篇 |
| `Home.jsx` 首屏以品牌介绍与探索按钮为主，搜索入口较小 | 好看，但不知道自己的问题应该从哪里进入 | 首屏突出搜索与“我想了解什么”的场景入口 |
| “今天多懂一点”固定展示血压内容 | 第一次像推荐，再回来发现没有变化 | 建立真实的编辑精选与更新记录；无每日更新能力时改叫“精选知识” |
| `Article.jsx` 所有文章沿用指标分工、过程链模板 | 无法承接检查准备、常见疑问、生活方式等内容 | 按内容类型组织模块，保留统一的阅读层级 |
| 器官名称、指标名称及文章到器官的部分映射写在组件里 | 扩容时容易出现入口与内容不同步 | 内容关系交由内容平台维护，前端只渲染可用关系 |
| 来源区已有引用，但全部内容是 `pending`，没有审校人记录 | 有参考链接，仍不知道是谁负责、何时复核 | 可核验的审校与编辑信息、纠错和版本记录 |
| 收藏仅限当前浏览器；没有阅读历史、专题进度 | 能收藏，但缺少完整的“下次回来”体验 | 匿名阅读历史、专题收藏、内容更新提示，之后再验证同步需求 |
| 文章初始 HTML 没有正文，导航主要是按钮 | 分享、外部搜索与内容发现能力弱 | 真实链接、独立文章元信息、公开内容预渲染 |

这些发现来自功能与代码检查，不等同于真实用户访谈结果。

## 2. 目标用户与使用场景

| 场景 | 用户想完成的事 | 第一阶段提供 | 暂不承诺 |
| --- | --- | --- | --- |
| 拿到体检结果 | 看懂某个缩写、指标或检查术语 | 术语搜索、通俗解释、影响因素、关联指标、就医沟通问题清单 | 根据个人数值判定疾病 |
| 自己或家人被提及某种健康问题 | 获得结构清楚、来源可靠的基础认识 | 常见疑问、疾病基础专题、检查与就医流程科普 | 代替医生选择治疗方案 |
| 想改善日常习惯 | 判断一种建议是否适合一般人 | 有适用条件的生活方式知识、误区澄清、延伸阅读 | 个性化处方、治疗效果保证 |
| 帮父母理解信息 | 把术语转成能读懂、能分享的解释 | 简洁摘要、大字号、带来源的分享卡片与稳定链接 | 利用焦虑促成付费或夸大风险 |

初始工作假设：先满足成年普通读者的体检与常见疑问需求。儿童、孕产妇、复杂慢病用药需要独立适用范围与审校资源，不直接套用成人内容。

## 3. 从产品、设计、工程三个角度提出候选功能

下列 15 项是候选池，不是同一版本的需求清单。

| 视角 | 功能构思 | 希望解决的问题 |
| --- | --- | --- |
| 产品 1 | 场景式知识入口：看体检、懂检查、认识疾病、健康生活 | 用户不知道专业词，也能找到方向 |
| 产品 2 | 体检专题包：术语解释、常见疑问、关联器官、准备事项 | 从零散单篇变成可以完成任务的知识集合 |
| 产品 3 | 向编辑提问与内容纠错 | 找不到答案时有反馈渠道，编辑获得真实需求 |
| 产品 4 | 主题关注与专题更新记录 | 下次回来有明确理由，避免重复固定推荐 |
| 产品 5 | 家人分享：一句话摘要、阅读链接、来源与日期 | 降低科普传播成本，保留内容语境 |
| 设计 1 | “30 秒先看懂”摘要 + 可展开的详细解释 | 同时照顾快速查找和深入阅读 |
| 设计 2 | 正文目录、预计阅读时间、大字号和阅读历史 | 让长内容可读、可定位、可继续 |
| 设计 3 | 人体、指标、常见问题的关联浏览 | 保留身体地图特色，同时让互动通往实际答案 |
| 设计 4 | 术语对照卡与常见混淆解释 | 降低缩写、相近概念带来的理解障碍 |
| 设计 5 | 不带健康评分的理解小测 | 帮用户检查是否理解，并给出解释和来源 |
| 工程 1 | 别名、中文缩写、英文缩写和容错检索 | 用户输入与专业标题不一致仍能找到内容 |
| 工程 2 | 版本绑定的来源与审校信息卡 | 内容变更后不会继续冒用旧审校状态 |
| 工程 3 | 公开文章预渲染、搜索引擎入口与分享元信息 | 从外部找到并直接读到正确文章 |
| 工程 4 | 匿名本地收藏、阅读进度与可清除历史 | 无需注册也有回访体验 |
| 工程 5 | 来源失效与内容复核提醒 | 维护者及时处理过期或改变的依据 |

## 4. 最值得先做的五组能力

缺少用户量与转化基线，暂不填造 RICE 数字。按用户影响、实现成本、内容成本、风险与定位匹配度排序。成本为相对大小，包含编辑与审校工作。

| 排名 | 能力 | 影响 / 成本 | 为什么现在做 | 需要验证的假设 |
| --- | --- | --- | --- | --- |
| 1 | 场景搜索与术语解释 | 高 / 中 | 对第一次访问立刻有用，也承接搜索引擎流量 | 用户最常查哪些原始词，别名搜索是否比浏览器官更直接 |
| 2 | 一个完整的主题内容库 | 高 / 高，主要在内容 | 解决“很快看完”和入口没有答案；建议先聚焦体检与代谢健康 | 该主题是否有稳定需求，编辑团队能否持续维护 |
| 3 | 分层文章阅读与关联路径 | 高 / 中 | 让内容看懂、看完并能继续了解，形成区别于文章堆积的体验 | 摘要、图示和常见疑问是否能改善复述理解 |
| 4 | 可信度信息与纠错闭环 | 高 / 中高 | 医学产品的基础信任，既保护读者也降低维护风险 | 用户是否理解审校状态，团队能否按承诺处理问题 |
| 5 | 专题收藏、历史与可追溯分享 | 中高 / 中 | 补齐保存、回访、向家人传播的完整链路 | 用户更需要主题回访还是账号同步；卡片是否带来有效阅读 |

内容平台和审校流程是第 2、4 项的基础，应提前建设，不能等“文章太多了”才开始。账号、社区和 AI 问答暂不进入前五：它们会增加运营与质量控制成本，却不能替代上述基础体验。

## 5. 第一阶段的具体产品形态

### 5.1 首页：先回答需求，再展示品牌

建议从上到下组织为：

1. 搜索框：“输入体检指标、英文缩写或你想了解的问题”。展示确实能找到内容的查询示例，不使用没有数据支撑的“热门”。
2. 3–4 个场景入口：看懂体检、检查怎么做、认识身体、常见健康疑问。仅在对应内容准备完成后展示入口。
3. 当前重点专题，例如“第一次看血脂报告”；一张卡片表达适合谁、能理解什么、包含几篇。
4. 编辑精选与最近更新；展示真实日期，发布频率由内容能力决定。
5. 人体关联探索，作为特色入口连接到指标和专题。
6. 最近阅读、收藏快捷入口，仅在有本地记录时出现。

保留现有绿色视觉风格，缩减移动首屏纯介绍面积。不需要依靠更多装饰性模块制造完整感。

### 5.2 知识文章：回答完一个问题

统一外层结构：标题 → 一句话结论 → 3 个关键点 → 正文目录 → 解释与图示 → 常见疑问 → 下一步可了解的内容 → 作者/审校/来源/版本 → 纠错入口。

内部根据类型选择模块：

- 指标类：是什么、检查目的、影响结果的因素、如何结合报告参考区间与其他信息理解、向医生询问哪些问题。
- 检查类：为什么做、准备事项、一般流程、结果由谁解释、特殊人群注意事项。
- 疾病基础类：基础概念、常见表现、诊断流程概述、预防与管理常识、误区；涉及就医警示的内容须有相应来源和审校。
- 健康生活类：建议适用人群、证据范围、如何理解常见说法、例外与限制。

不把“参考范围”“诊断阈值”“治疗目标”合成一个正常值。没有审校依据时不展示用户数值打分或红绿灯判断。

### 5.3 内容规模：看覆盖，不凑数量

可将首批完整主题规划为约 20–30 个经审校的独立知识页，这是编辑排期参考，不是上线数量硬指标。先建立术语与问题清单，再判断哪些适合合并为专题、哪些适合独立页面。

选题示例：已有血糖、血脂、血压专题补齐常见疑问；肝功能、肾功能、血常规、尿常规作为候选扩展；检查前准备、为什么参考范围不一样、单次异常该如何理解作为跨专题解释。具体医疗内容需在正式编辑时逐条寻找依据。

至少一个主题应具备：入口页、关联术语、基础说明、常见问题、完整来源、审校记录与有效的下一步链接。只完成 12 个有用页面，也比 100 个薄弱页面更适合作为初次产品发布。

### 5.4 完整产品必备但不必夸大的细节

- 关于知愈、编辑原则、作者与审校人介绍、内容更新时间解释。
- 内容纠错表单与处理状态；收集文章 ID 和问题描述，避免要求用户上传个人报告。
- 真实 404、撤稿说明、搜索无结果引导、网络失败重试。
- 大字号、键盘与读屏支持、减少动画偏好、真实手机与微信内置浏览器验证。
- 收藏与历史的本地存储说明、清除入口；未来增加服务端采集时同步完善隐私说明。
- 分享标题、摘要与缩略图与当前文章一致；二维码或卡片标明版本日期，原始链接可查看更新。

## 6. 可信医学内容如何体现在界面

在正文附近简洁呈现“谁整理、谁审校、适用范围、最后医学复核时间”。来源列表保留，但参考资料数量不作为质量评分。未完成专业审校的内容明确显示状态；不能把一个 `reviewed` 字符串当作可信凭证。

来源、编辑、审校三个角色分开：WHO 等机构是参考资料发布者，并不因此为知愈背书；内容编辑负责通俗表达；医学审校人对具体内容版本负责。作者与审校人信息的展示以真实授权资料为准，不生成虚构医生身份。

后台必须能处理“某个依据变了，哪些文章、摘要、分享卡片需要复核”。详情见 [内容平台方案](knowledge-platform.md)。

## 7. 用户吸引与回访机制

获客：以具体疑问和术语的公开文章承接自然搜索；用带来源的摘要和专题链接促进家人分享；公众号以精选内容引导进入专题。标题描述实际问题，不用疾病恐吓和夸大疗效吸引点击。

首次体验：无需注册即可查找、阅读、收藏。先给出可读结论，再提供展开与原文核验入口。向新用户解释一次“收藏在本机”，不反复阻挡阅读。

回访：围绕专题、后续阅读和已收藏内容的修订提醒建立理由。内容产品可能是低频工具，不把连续签到、使用时长和每日打开次数作为首要目标。

增长假设：用户解决问题 → 保存/分享准确解释 → 新读者打开对应文章 → 自己再次查找。应测量是否产生有效阅读，而非仅看分享按钮点击数。

## 8. 如何验证方向

第一轮邀请至少 5–8 位目标读者，用同一组任务观察：找到一个缩写、用自己的话解释关键概念、辨认适用范围、找到审校与来源、收藏后再次打开。先记录失败原因，再设后续提升目标。

| 指标 | 初始定义 | 使用限制 |
| --- | --- | --- |
| 查找任务完成率 | 测试任务中找到匹配答案的比例 | 小样本仅用于定位体验问题，不代表全体用户 |
| 理解任务完成情况 | 对关键概念复述是否正确、是否出现危险误解 | 需要预先制定答案与审校标准，不能靠阅读时长推断 |
| 搜索无结果率 | 有效查询中未得到可用结果的比例 | 内部查询集先跑通；公开原始查询可能含健康隐私，不默认持久化 |
| 阅读帮助度 | 自愿反馈“是否解决本次问题”及原因 | 是反馈信号，不是医学准确性证明 |
| 专题回访与分享后阅读 | 按主题观察后续访问和有效打开 | 没有账号时只能形成有限的浏览器级估计 |
| 内容质量 | 审校覆盖、到期复核、错误处理时间、失效来源 | 对正式发布内容分别统计，不与演示内容混算 |

一旦有真实基线，再决定主题范围、发布节奏和增长目标。不会在当前阶段虚构留存提升比例或市场规模。

## 9. 阶段边界与待决策项

第一阶段不建设开放病友社区、在线问诊、个体化 AI 诊断、药品购买推荐、个人报告分析。若以后引入 AI，可先做仅基于已审校内容的编辑辅助或检索解释，并单独验证引用、拒答和质量控制；不能自动生成并发布医学结论。

需要维护者确认的决策是内容生产能力与审校资源、首个聚焦主题、开源许可证、是否有商业化计划（影响内容授权）。这些决策不妨碍先完成信息架构、来源登记、内容模型和 History 基础改造。
