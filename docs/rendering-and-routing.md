# History 路由与页面渲染决策

日期：2026-09-19。结论：History 路由本轮落地；面向大众搜索和分享的公开知识页建议下一阶段采用 SSG / ISR 预渲染；不建议为了更换 URL 就将整个网站改为每次请求动态 SSR。

## 1. 三个不同的问题

- **History 路由**决定地址形式，例如 `/article/glucose`；它需要服务器支持直接打开和刷新，不决定正文在哪里生成。
- **CSR / SSG / SSR**决定浏览器收到的 HTML 是否已经有正文，以及什么时候生成正文。
- **CMS 与数据库**决定知识如何维护、审校和发布；即使有数据库，公开文章仍可以静态生成。

所以“加后端 → 全站 SSR”和“History → SEO 已解决”都不成立。应按页面是否公开、更新频率、交互程度与搜索价值分别选择。

## 2. 当前页面展示评估

当前 `index.html` 只提供页面容器与通用标题、描述。React 在浏览器运行后加载 JSON，文章标题和正文才出现。正文引用、收藏和器官互动表现适合客户端执行，但这个初始 HTML 对不执行 JavaScript 的抓取工具不完整。

`main.jsx` 在客户端设置页面标题，文章页仍使用通用“指标解读”；没有按文章生成独立描述、canonical 或 Open Graph 元信息。卡片与导航主要是按钮，不能只通过 HTML 链接结构发现整个内容库。以上问题影响外部内容发现，与界面的视觉完成度是不同维度。

Google 可以渲染部分 JavaScript 页面，不能断言 SPA 永远不会被收录；但渲染并非对所有机器人都成立，也不能保证各平台分享抓取会运行页面脚本。对于依赖大众自然搜索获客的医学科普产品，服务端输出可读 HTML 值得作为公开内容基础能力。

## 3. 本轮 History 改造范围

| 页面 | 新路径 | 旧链接兼容 |
| --- | --- | --- |
| 首页 | `/` | `/#/map` 在浏览器转换为 `/` |
| 指标目录 | `/indicators` | `/#/indicators` 转换为新路径 |
| 器官 | `/organs` 或 `/organs/heart` | 旧器官 Hash 链接保持对应目标 |
| 收藏 | `/saved` | 旧收藏链接转换，已有本地数据不变 |
| 指标文章 | `/article/glucose` | `/#/article/glucose` 转换为新路径 |

实现要点：

- 路由解析读取 `location.pathname`，导航使用 `pushState`，前进/后退使用 `popstate`。
- 用 `replaceState` 将可识别的旧 `#/...` 转成新路径，不额外增加一条历史记录；保留原查询参数，普通正文锚点不当作页面路由。
- 不改变现有文章 ID、器官 ID 和收藏的存储键，因此已有收藏无需迁移。
- Nginx 仅对已定义的应用路径回退到 `index.html`；`/assets/`、`/content/` 的缺失资源仍返回 404，不返回 HTML 伪装数据。
- 语法不合法的路径由服务端 404 或客户端不存在页面处理，不再默默展示首页。
- 当前只配置域名根路径部署。未来如果部署在子目录，路由 basename、Vite base 和服务器规则需要统一设计，不把根路径实现直接用于子目录。

旧 URL 的 `#` 后部分不会送到服务器，所以不能靠 Nginx 对旧文章 Hash 做逐篇 301；浏览器兼容迁移是必要措施。

### 当前仍存在的限制

结构合法但不存在的文章，例如 `/article/not-a-real-topic`，SPA 页面壳仍可能返回 HTTP 200，再由前端显示内容不存在。它是后续预渲染/服务端路由要解决的 soft 404 问题，本轮不宣称已实现内容级真实 404。

History 改造不提供独立正文 HTML、逐篇 SEO 元信息、分享图片、服务端内容查询或中文全文搜索。公开文章相关功能仍按下一阶段安排。

## 4. 推荐的逐页渲染策略

| 页面类型 | 建议方式 | 原因 | 缓存与索引 |
| --- | --- | --- | --- |
| 首页、主题入口、分类页 | SSG / ISR | 公开且大部分读者看到相同内容 | 发布事件更新，可被搜索发现 |
| 指标、疾病基础、检查说明文章 | SSG / ISR 优先 | 变化频率低于访问频率，正文与来源应直接在 HTML 中 | 按内容版本刷新，生成 sitemap 与独立元信息 |
| 器官知识页 | 文字预渲染 + 客户端交互图 | 文字可读与动画交互可以分开 | 已发布内容可索引，图形模块按需加载 |
| 搜索结果 | 页面框架 + 客户端请求，必要时 SSR 首屏 | 组合很多，不必为每个查询预生成页面 | 搜索参数页通常 noindex，防止重复与低价值页面膨胀 |
| 收藏、历史、账号 | 客户端交互或认证动态页 | 私人状态，不应进入公共缓存或索引 | noindex；含用户数据时 private/no-store |
| CMS 与预览 | 认证动态渲染 | 草稿与管理信息不能公开 | 不进入公开 CDN 缓存或 sitemap |

SSG 是发布或构建时生成；ISR 是使用缓存页面并在指定条件下重新生成；动态 SSR 是每次请求生成。对于当前知识页，内容发布事件驱动的更新比每次访问都读取数据库更符合需求。

真实撤回需额外机制：不能只依赖 ISR 的正常过期窗口。需要立即生效的撤回状态和缓存失效流程，详见 [知识平台方案](knowledge-platform.md)。

## 5. 框架与迁移选择

建议在内容后台原型与页面数据模型稳定后，将公开网站迁移到 Next.js App Router，沿用 React 组件与样式，将公开内容数据在服务端读取并传入页面。选择在实施时仍受支持、经过验证的版本，不在本方案中绑定某个“最新”缓存 API。

主要理由是可复用现有 React 实现，同时支持公开内容预渲染、动态路由、独立元信息、状态码和后续账号动态页面。Payload 与 Next.js 的组合可以进一步减少技术栈分散，但不是采用 Next.js 的唯一前提。

备选方案：保留 Vite 并接入成熟的预渲染方案，适合只维护少量静态文章的阶段；Astro + React 也适合内容型网站。如果团队长期只做静态百科、不做账户与复杂应用，Astro 值得对比。当前已有较多应用式交互并计划建设后台，优先验证 Next.js 的综合成本。

不建议自写一套浏览器截图式“伪预渲染”作为长期基础。它难以正确处理鉴权、失败状态、撤稿、更新一致性和内容规模。

## 6. 迁移前必须改的代码组织

- 将文章正文和来源展示组件与收藏、分享、浏览器存储等交互分开。
- 当前 `useRoute`、`useBookmarks` 和部分组件访问 `window` / `localStorage`，不能原样在服务器执行；客户端状态应在挂载后恢复，避免 hydration 不一致。
- 将 `useContent` 的浏览器 effect 数据获取与服务端已发布内容查询分开，避免 HTML 有正文后客户端再次闪回加载态。
- 将卡片和跨页面导航改成真实的可访问链接；保留按钮用于切换、收藏和交互操作。
- 标题、摘要、canonical、Open Graph、作者/审校和日期从同一已发布修订产生，不能拼出与正文不一致的另一版本。
- 从可公开内容生成 sitemap；分页、查询参数、撤回内容、草稿与预览链接有明确索引规则。
- 对不存在的内容返回真正的 404；撤回内容按产品政策提供更正说明或 410。服务器错误不伪装成成功页面。
- 结构化数据只描述真实可见且有依据的信息。使用 `Article` / `MedicalWebPage` 等适当类型不保证获得搜索富结果，也不提供“医学权威认证”。

## 7. 验证与发布门槛

History 阶段：直接打开文章、刷新、返回/前进、旧链接转换、查询参数保留、收藏不丢失、缺失资源 404、无脚本异常。

预渲染阶段：

1. 使用不执行 JavaScript 的 HTTP 客户端获取文章，返回体含对应标题、摘要、正文、来源和日期，而不是仅有 `root` 容器。
2. 检查页面 metadata、canonical 和可抓取链接；在实际分享平台验证标题和缩略图，不能只依据浏览器内显示判断。
3. 微信自定义分享卡片如需要 JS-SDK，应单独做合法域名、签名和权限配置；SSR / Open Graph 不自动替代微信平台要求。
4. 内容发布、修订、撤回后，页面、API、主题索引与分享元信息一致，失败有可观察的重试记录。
5. 草稿与用户数据不进入公开 HTML 或共享缓存；未知与撤回 URL 返回预期状态码。
6. 测量真实移动端首屏与交互。可参考 Core Web Vitals 常用目标，但缺少真实样本前不宣称达标或承诺搜索排名。
